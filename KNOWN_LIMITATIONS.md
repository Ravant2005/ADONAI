# ADONAI — Known Platform & Operational Limitations

1. **Android Application Sandboxing**: Android isolates each application's private SQLite databases and internal storage. ADONAI cannot read WhatsApp, Signal, or banking app internal databases. Instead, it analyzes `PackageManager` permission grants, user-shared content (`ACTION_SEND`), and opt-in notification fields actually exposed by Android.
2. **Encrypted TLS Payloads**: The opt-in `AdonaiVpnService` inspects DNS queries and socket metadata (destination IP, port, byte counts, timing). It does **not** install a root CA or perform MITM TLS decryption on third-party traffic. Outbound volume anomalies following sensitive resource access are explicitly labeled `INFERRED`, never `CONFIRMED` exfiltration.
3. **1,000 Cyber-Range Nodes**: The 1,000 nodes rendered in the 3D Cyber Range correspond to 1,000 individual `SimulatedEndpoint` records in SQLite (`sim-ep-0001` to `sim-ep-1000`) with distinct virtual IPs and sector profiles. They represent virtual endpoint identities for deterministic telemetry emulation and correlation testing, not 1,000 full virtual machine operating systems.
4. **Local LLM Availability**: When an Ollama or OpenAI-compatible local inference server (`127.0.0.1:11434`) is not running on the host machine, ADONAI automatically uses its deterministic, JSON-schema-validated fallback explainer (`DETERMINISTIC_FALLBACK`) so detection and user guidance remain 100% operational offline.
5. **External Threat Feed Keys**: Sources requiring personal API keys (e.g., AbuseIPDB, Have I Been Pwned v3, private MISP/OpenCTI instances) report `OFFLINE_OR_API_KEY_REQUIRED` until environment credentials are supplied. ADONAI never fabricates live feed data when offline.
